# C.A.I.R.O Architecture Overview
*Certificate Automated Intelligent Renewal Operations — Mississippi ITS / MDA*

## System Components

The CSR Certificate Lifecycle Management PoC consists of three main layers:

### 1. React Frontend (port 8081)
- Built with React 18 + TypeScript + Vite 5
- shadcn/ui component library (Radix primitives + Tailwind CSS)
- Five dashboard sections: Overview, Certificates, Alerts, Agent Activity, Settings
- Communicates with the Flask API via `src/utils/api.ts`

### 2. Flask REST API — `api_bridge.py` (port 5000)
- Loads certificate inventory from CSV + parses real `.crt` files on startup
- Runs the RenewalAgent against all expiring/expired certs at boot
- Builds notification list; sends startup SNS bulk alert (configurable)
- Starts background threads: daily digest loop (checks every 5 min) and weekly report loop (checks hourly)
- Exposes 30+ REST endpoints; CORS restricted to localhost:8081

### 3. RenewalAgent — `renewal_agent.py`
- 6-step pipeline per certificate: detect → csr_generation → ca_submission → cert_issuance → deployment → validation
- CSR generation is **real crypto** (RSA 2048, SHA-256, via Python `cryptography` library)
- **Step 3:** Real Entrust API call when credentials are set;
  internal CA fallback when unavailable or on any error.
- Certificate issuance uses internal Mississippi ITS Root CA signing (and PFX when `CA_PFX_PASSWORD` is set); deployment notification and validation are partially automated

## Data Flow

```
CSV Inventory + .crt files
        │
        ▼
Flask API (api_bridge.py) ──────────────── AWS SNS (email alerts)
        │                                        │
        ├── RenewalAgent ─── writes CSRs/keys    │
        │        │           to generated_certificates/
        │        └── Amazon Bedrock (AI risk analysis)
        │
        ▼
React Frontend (port 8081)
        │
        └── User Dashboard (5 sections)
```

## AWS Services Used

| Service | Status | Purpose |
|---------|--------|---------|
| AWS SNS | ✅ Active | Email alerts (per-cert, daily digest, weekly report, startup) |
| Amazon Bedrock (Nova Lite) | ✅ Active | AI urgency scoring (0–100), risk levels, recommended actions |
| Amazon S3 | ✅ Active | CSR files, private keys, issued certificates, PFX bundles |
| AWS DynamoDB | ✅ Active | Certificate inventory, notifications, agent jobs, settings, email log |
| AWS Cognito | ✅ Active | JWT verification + admin/operator RBAC implemented; enterprise SSO/MFA planned for production |
| AWS KMS | 🔲 Planned | Encryption for private keys at rest (currently S3 only) |

**DynamoDB tables (all active in PoC):**
- `cert-lifecycle-certificates` — certificate inventory
- `cert-lifecycle-notifications` — alert history
- `cert-lifecycle-email-log` — email audit trail
- `cert-lifecycle-agent-jobs` — pipeline job state
- `cert-lifecycle-settings` — notification preferences

## Certificate Status Ladder

| Condition | Status |
|-----------|--------|
| days_to_expiry < 0 | `expired` |
| 0 ≤ days ≤ 7 | `critical` |
| 7 < days ≤ renewal_threshold | `expiring_soon` |
| days > threshold | `active` |

## Sandbox Notes

- All certificate files are self-signed dummy certs generated by `generate_dummy_certificates.py`
- The inventory covers 20 representative certificates across 8 Mississippi agencies
- Date mode is "simulated" by default — CSV expiration dates drive status computation
- DynamoDB, S3, SNS, and Amazon Bedrock are **active AWS services** wired to the live system
- No production systems, real agency certificates, or live private keys were used
- **Step 3:** Real Entrust API call when credentials are set;
  internal CA fallback when unavailable or on any error.
- The internal Mississippi ITS Root CA issues certificates when Entrust is unavailable or fails

## C.A.I.R.O 6-Step Pipeline

```
1. detect          → Record trigger reason, days_to_expiry, AI urgency score
2. csr_generation  → Real RSA-2048 / SHA-256 CSR + private key (cryptography library)
3. ca_submission   → POST CSR to Entrust cloud CA when credentials
                     are configured; falls back gracefully to internal
                     CA on any failure. Never blocks step 4.
4. cert_issuance   → Receive issued cert + create PFX bundle [SIMULATED]
5. deployment      → Email ITS with PFX import checklist; ITS confirms in dashboard
6. validation      → Post-deployment check; audit trail closed by ITS confirmation
```

**Steps 1–2:** Real cryptography (Bedrock AI + RSA-2048 CSR generation).
**Step 4:** Real signing — internal Mississippi ITS Root CA produces
a trusted `.crt` and PKCS#12 PFX bundle.
**Step 5:** Half-automated — real SNS email with import checklist;
ITS manually imports PFX into IIS and updates FortiManager.
**Step 3:** Real Entrust API call when credentials are set;
internal CA fallback when unavailable or on any error.
**Step 6:** File-existence check only — live TLS probe against
the deployed site is not yet implemented.
